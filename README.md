# skkserv-compound

SKK 辞書をパーツとして連結し、辞書未登録の連結語を補助候補として返す skkserv です。

例:

- `せいそうぎょうしゃ` → `せいそう` + `ぎょうしゃ` → `清掃業者`
- `たんじゅんか` → `たんじゅん` + `か` → `単純化`

abbrev エントリ (ASCII 見出し語) も同じアルゴリズムで連結部品として使います。たとえば辞書に `mini /ミニ/`, `catalog /カタログ/`, `gift /ギフト/` が入っていれば、`minicataloggift` → `mini` + `catalog` + `gift` → `ミニカタログギフト` のように ASCII 入力に対する連結候補が生成されます。

送り仮名つき入力にも対応します。たとえば `もんだいなs` (= `もんだい` + 送り `s`) のように送りつき見出しを受け取った場合、`もんだい /問題/` と `なs /無/` から `問題無` を返します。送り仮名 hiragana (`し` など) はサーバー側では付加しません — SKK 慣習どおりクライアントが補います。

「賢い変換器」ではなく「既存辞書語を組み合わせる補助辞書サーバー」として振る舞います。

## 使い方

```sh
skkserv-compound \
  --bind-address 127.0.0.1 \
  --port 1178 \
  --incoming-charset EUC-JP \
  --user-dictionary ~/.skk-jisyo \
  --system-dictionary /path/to/SKK-JISYO.L \
  --system-dictionary /path/to/SKK-JISYO.jinmei
```

| Option | Default | 説明 |
|---|---|---|
| `--user-dictionary` | (required) | SKK ユーザー辞書ファイルへのパス。起動後はファイル変更を監視して reindex します |
| `--system-dictionary` | なし | システム辞書ファイルへのパス。複数回指定でき、左に書いたものほど優先されます (同じ読み・同じ候補が複数の system 辞書に現れた場合は最初に指定された辞書由来として扱います) |
| `--bind-address` | `127.0.0.1` | bind するネットワークアドレス (`0.0.0.0` で全インターフェース) |
| `--port` | `1178` | listen ポート |
| `--incoming-charset` | `UTF-8` | クライアントが送ってくる文字コード (`UTF-8` または `EUC-JP`) |
| `--max-candidates-per-reading` | `5` | 各読み片から使う候補数の上限 |
| `--max-final-candidates` | `10` | 最終出力候補数の上限 |
| `--log-level` | `notice` | ログレベル (`trace`/`debug`/`info`/`notice`/`warning`/`error`/`critical`) |

## 候補生成のルール

- **連結語数**: 最小 2、上限なし (yomi 文字数まで)。best-first で必要な分だけ展開し、最終候補数上限に達した時点で以降の探索を打ち切ります
- **順位**: ① 語数が少ない分割 → ② 分割の最短部分が長いもの → ③ 同 ② で並ぶ分割間ではラウンドロビン (各 split の 1 番目候補をすべて先に出し、続けて 2 番目候補をすべて出す。同 rank 内は辞書登録順) → ④ 各読み片の候補順位
- **候補順位**: 同一読み内では user 辞書候補が system 辞書候補より優先。各 source 内では辞書ファイルの出現順を尊重します
- **1 語完全一致は返しません**。クライアントが通常の辞書検索で出すためです
- **候補文字列は部品の表記をそのまま結合**します。送り仮名 hiragana の付加、活用、表記調整は行いません
- **短い読み** (`か`, `し`, `ご` 等) も辞書にあれば連結部品として使います
- **意味判定はしません**。`単純蚊` のような不自然な候補を完全に消すことはせず、順位と候補数上限で実用上見えにくくします
- **意味的なフィルタが必要なら user 辞書での学習に委ねます**。SKK クライアントが選んだ候補は user 辞書に反映され、次回以降の順位に効きます

優先度キーの完全な順序、cap の作用、okuri-ari の制約、round-robin と dedupe の挙動などの詳細仕様は [docs/candidate-ranking.md](docs/candidate-ranking.md) を参照してください。

## 辞書のマージ規則

複数の system 辞書と user 辞書は同じ parser で読み、内部で 1 つの index にマージされます。

- source の優先順位: **user > 先に指定された system > 後に指定された system**
- 同じ読み・同じ候補が複数の source に現れた場合は、最も優先される source 由来として 1 件だけ残します
- 同じ読み内では user 候補をまず並べ、続いて system 候補を CLI 指定順で並べます

送りあり (okuri-ari) エントリは送りなしエントリとは別バケットで保持し、送り仮名つきリクエスト時にのみ参照されます。

## 非目的

このサーバーは「賢い変換器」ではなく「既存辞書語を組み合わせる補助辞書サーバー」です。以下は意図的に扱いません:

- ニューラルかな漢字変換 / 文法的自然さの判定 / 品詞推定
- 1 語完全一致候補の返却
- 補完候補の生成 (opcode `4` は常に `4\n`)
- 送り仮名 hiragana の挿入や活用変換 (連結漢字部分だけを返し、送り仮名はクライアントが補う)
- 長文変換
- GUI アプリ

## skkserv プロトコル

| opcode | operand | 出力 |
|--------|---------|------|
| `0`    | なし    | コネクションを閉じる |
| `1`    | 見出し語 | 候補あり: `1/{候補1}/{候補2}/.../{候補n}/\n` / 候補なし: `4\n` |
| `2`    | なし    | `skkserv-compound/{version} ` |
| `3`    | なし    | `{ホスト名}/{IP}:{ポート} ` |
| `4`    | 見出し語 | 常に `4\n` (補完は提供しません) |
